.deb Package Anatomy (Debian/Ubuntu)
A .deb is an ar archive containing 3 members:
debian-binary — format version (always "2.0")
control.tar.gz — metadata: package name, version, depends, conflicts, maintainer scripts (preinst, postinst, prerm, postrm)
data.tar.xz — actual files to install, paths relative to /

dpkg -x package.deb /tmp/extract — extract files
dpkg -e package.deb /tmp/ctrl — extract control
.rpm Package Anatomy (RHEL/Fedora)
A .rpm is a custom binary format with header + CPIO payload:
Lead — magic number, format version
Signature section — GPG signature, MD5/SHA256 of header+payload
Header — name, version, release, arch, requires, conflicts, scripts
Payload — CPIO archive (files to install)

rpm -qpl package.rpm — list files
rpm -qpi package.rpm — show info
🐧apt — Advanced Package Tool (Debian / Ubuntu)PANEL 02
apt vs apt-get vs dpkg
dpkg — low level: installs/removes individual .deb files. No dependency resolution. No repository access.
apt-get — classic CLI with dependency resolution. Stable API for scripts.
apt — modern frontend: prettier output, progress bars, combines apt-get + apt-cache + apt-config. Use apt for interactive use.
aptitude — ncurses UI + smarter conflict resolution.
Repository Configuration
/etc/apt/sources.list — main repo list
/etc/apt/sources.list.d/*.list — per-repo files
/etc/apt/sources.list.d/*.sources — DEB822 format (modern)

Format: deb [arch=amd64 signed-by=/key.gpg] https://repo.example.com focal main

Components: main (free+supported), restricted (proprietary drivers), universe (community), multiverse (non-free)

🎩dnf / yum — Red Hat Package ManagementPANEL 03
dnf vs yum vs rpm
yum — legacy (RHEL 6-7, CentOS 7). Python 2. Slow. Still works on RHEL 7.
dnf — modern replacement (RHEL 8+, Fedora). Python 3. Faster, libsolv resolver, modular repos.
rpm — low-level tool. Install individual .rpm files. Query package database.

dnf is a superset of yum commands — switching from yum to dnf is almost drop-in.
DNF Repositories
/etc/yum.repos.d/*.repo — repo config files

Key repos:
BaseOS — core OS packages
AppStream — applications + modules
EPEL — Extra Packages for Enterprise Linux (community)
RHEL CodeReady — dev tools
RPM Fusion — multimedia, proprietary

EPEL is the community-equivalent of Ubuntu's universe repo.

🔏GPG Signatures & Repository SecurityPANEL 05
ℹEvery legitimate Linux repository uses GPG (GNU Privacy Guard) to sign packages and repository metadata. Your package manager verifies these signatures before installation. A compromised or unsigned package = potential supply chain attack.
GPG Package Verification Chain
🏢
Distro/Maintainer
Signs package with private key. Signs repo InRelease/Release.gpg metadata.
→
☁️
Mirror CDN
Distributes signed packages worldwide. Mirror cannot tamper — signature would break.
→
📥
apt/dnf Download
Downloads package + detached signature (.sig or embedded in Release file).
→
🔑
Local Keyring Verify
apt-key / /etc/apt/keyrings/ holds trusted public keys. Signature verified cryptographically before install.
→
✅
Install Proceeds
Only if ALL signatures valid. Any mismatch = hard error, installation aborted.

🕸Dependency Resolution — How It WorksPANEL 06
Dependency Graph Resolution
When you install package A, the resolver builds a directed acyclic graph (DAG) of all dependencies. It uses SAT solving (apt uses EDSP, dnf uses libsolv) to find a consistent set of packages satisfying all version constraints.

Dependency hell = when two packages require incompatible versions of the same library. Solutions: virtual packages, alternatives, parallel library versions (lib32, lib64).
Dependency Types
Depends — must be installed. Hard requirement.
Recommends — installed by default but can skip with --no-install-recommends
Suggests — optional enhancement, not installed by default
Conflicts — cannot be installed alongside
Breaks — installing this breaks another
Replaces — supersedes another package
Provides — virtual package: satisfies another's dependency

🔨Building from Source — Compilation & InstallationPANEL 08
ℹBuilding from source gives complete control: custom compile flags, optimisations, features, and the ability to patch before building. Required for: bleeding-edge software, custom modules, security patches not yet in repos, or software not packaged for your distro.
1
Install Build Dependencies
Compilers (gcc/clang), make, autoconf, pkg-config, and all library dev headers (-dev/-devel packages).
apt install build-essential gcc make autoconf pkg-config libssl-dev libpcre2-dev zlib1g-dev
2
Get Source Code
Download tarball or clone repository. Verify tarball GPG signature before use.
wget https://nginx.org/download/nginx-1.25.4.tar.gz
wget https://nginx.org/download/nginx-1.25.4.tar.gz.asc
gpg --verify nginx-1.25.4.tar.gz.asc nginx-1.25.4.tar.gz
3
Extract & Configure
Run ./configure to detect system capabilities, set install paths, enable/disable features. Generates Makefile.
tar xzf nginx-1.25.4.tar.gz && cd nginx-1.25.4
./configure --prefix=/usr/local/nginx --with-http_ssl_module --with-http_v2_module --with-pcre
4
Compile
make invokes gcc/clang for each source file, links object files into final binary.
make -j$(nproc) # parallel build using all CPU cores
5
Test (Optional but recommended)
Run included test suite before installing. Catches issues before they affect the system.
make test # or: make check
6
Install
make install copies files to --prefix location. Consider checkinstall to create .deb/.rpm for proper package management.
make install # OR: checkinstall --pkgname=nginx-custom --pkgversion=1.25.4

🔒Supply Chain Security — Attack Vectors & DefencesPANEL 09
Supply Chain Attack Vectors
  • ›
    Typosquatting: Attacker uploads ngynx or ngnix to PyPI/npm. User typos → installs malicious package with legitimate-looking name.
  • ›
    Dependency confusion: Internal package named "mycompany-utils" — attacker uploads public package with same name at higher version → npm/pip prefers public version.
  • ›
    Compromised maintainer: Attacker steals PyPI/npm credentials → pushes malicious update to legitimate popular package (XZ Utils CVE-2024-3094).
  • ›
    Unsigned packages: Installing packages without GPG verification → any MITM on the download can inject malicious code.
  • ›
    Malicious PPA/repo: User adds untrusted PPA → all packages in that repo can be pushed to the system.
Supply Chain Defences
  • ›
    Always use distro repositories first — they have package review processes. Third-party repos require additional trust.
  • ›
    Verify GPG signatures on tarballs before building from source. Check fingerprint against multiple sources.
  • ›
    Pin package versions in production: apt-mark hold or version-pinned in requirements.txt. Prevent unexpected updates.
  • ›
    Use dpkg --verify / rpm -Va regularly to detect tampered installed files.
  • ›
    SBOM (Software Bill of Materials) — document every package and version. Use syft, grype for container image scanning.

🏢Enterprise Package Management — Mirrors, Proxies & AutomationPANEL 11
Private Mirror / Repository
In enterprise environments, expose servers directly to internet repos = risk. Solution: internal mirror.

Tools: apt-mirror / Nexus Repository / Artifactory / Pulp.

Benefits: airgapped installs (no internet), bandwidth savings (one download for all servers), version control (choose which packages reach production), security scanning before promotion to prod.
Automated Patching Strategy
DEV → apply all patches immediately, test
STAGING → apply after 48h, regression test
PRODUCTION → apply after 1 week validation

Tools: Ansible (apt module), Puppet, Chef.
Automation: unattended-upgrades for security patches. Manual for kernel (requires reboot window).

Rollback: apt-mark hold + snapshot LVM/Btrfs before upgrade.

Package Managers
apt (Debian/Ubuntu), dnf (RHEL/Fedora), pacman (Arch), apk (Alpine). Each has a low-level tool (dpkg/rpm) and high-level frontend. GPG signatures are non-negotiable — always verify. Use distro repos first, third-party with caution.
Dependency & Formats
Package managers automatically resolve dependency DAGs. Snap/flatpak provide cross-distro sandboxed packages — flatpak better for desktop, snap for server daemons. Build from source: configure → make -j$(nproc) → checkinstall for tracking.
Security & Enterprise
Supply chain risks: typosquatting, dependency confusion, compromised maintainer (XZ Utils). Defences: GPG verify, dpkg --verify, pin versions, internal mirrors, SBOM, trivy/grype scanning. Ansible automates patching at scale.
