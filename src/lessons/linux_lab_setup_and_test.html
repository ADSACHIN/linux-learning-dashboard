🖥Lab Environment Options — Choose Your SetupPANEL 01
ℹYou need at least one Linux VM for individual exercises, and 3–5 VMs for the full enterprise lab topology. All options below work — choose based on your host OS and hardware.
📦
VirtualBox
RECOMMENDED — BEGINNER
Free, works on Windows/macOS/Linux. GUI for creating VMs. Supports snapshots, NAT networking, host-only adapters. Ideal for multi-VM labs.
⚡
KVM / libvirt
RECOMMENDED — LINUX HOST
Best performance on Linux. Native hypervisor. Use virt-manager for GUI or virsh CLI. Near-bare-metal speed. Already covered in Step 10.
🐳
WSL2 + Docker
QUICK START — WINDOWS HOST
WSL2 gives real Linux kernel on Windows. Docker Desktop for containers. Good for individual exercises. Limited for full HA/networking labs.
☁️
Oracle Cloud Free Tier
FREE CLOUD — ALWAYS-ON
4 Ampere A1 cores + 24GB RAM free forever. Perfect for persistent lab. Public IP. Real SSH practice. Deploy full topology here.
🚀
Vagrant + VirtualBox
AUTOMATED — REPRODUCIBLE
Vagrantfile describes entire lab. vagrant up creates 5 VMs in minutes. Destroy and rebuild instantly. Best for repeatable lab exercises.
🎮
TryHackMe / HackTheBox
ONLINE — SECURITY FOCUS
Browser-based Linux rooms. Pre-configured vulnerable machines. Great for practising Steps 4, 6, 7 (security). No setup required.

🧪Practical Exercises — Steps 1–6 (Kernel to Networking)PANEL 04
LAB 01 — SYSTEM EXPLORATION
Map the entire system — from CPU to kernel to processes
SSH into lab-web. Without looking up answers, document the system: kernel version, distro, CPU architecture, loaded modules, running process tree, all open ports, all listening sockets, and the path every packet takes from curl lab-lb to nginx.
uname -a; cat /etc/os-release; lscpu | grep -E "Arch|CPU|Model"
lsmod | head -15; pstree -p | head -20
ss -tlnp; ip route show; ip addr show
strace -c curl http://lab-lb 2>&1 | tail -10 # trace syscalls
✓ VERIFY: Can you explain where nginx is in the process tree, which FDs are open, and what the default route is?
LAB 02 — FILESYSTEM FORENSICS
Investigate every directory and permission in the system
On lab-web: find all SUID binaries, all world-writable files, all files modified in the last 24 hours, and the inode of /etc/passwd. Explain the permission string of every file in /usr/bin/sudo's directory.
find / -perm -4000 -type f 2>/dev/null | sort
find / -perm -002 -not -path '/proc/*' -type f 2>/dev/null
find / -newer /etc/passwd -not -path '/proc/*' -type f 2>/dev/null | head -20
stat /etc/passwd; ls -lai /etc/passwd; df -i /
✓ VERIFY: Did you find any unexpected SUID binaries? Any world-writable files outside /tmp? Note them.
LAB 03 — USER & PERMISSION MANAGEMENT
Build a multi-user environment with proper access controls
Create users: alice (developer), bob (read-only auditor), carol (deploy account). Set up a /shared/project directory where alice has rwx, bob has r-x, carol has rwx, but no other users. Use ACLs. Then prove bob cannot delete alice's files.
useradd -m -s /bin/bash alice bob carol
mkdir -p /shared/project && chmod 750 /shared/project
setfacl -m u:alice:rwx,u:bob:r-x,u:carol:rwx /shared/project
setfacl -d -m u:alice:rwx,u:bob:r-x,u:carol:rwx /shared/project
su - bob -c "rm /shared/project/alice_file.txt" 2>&1 # should fail
✓ VERIFY: getfacl /shared/project shows correct ACLs. Bob cannot delete alice's files. Carol can write.
LAB 04 — SERVICE MANAGEMENT & SYSTEMD
Deploy a hardened web application as a systemd service
Create a Python Flask app that serves /health (returns 200 OK) on port 8080. Write a production systemd unit with: non-root user, PrivateTmp, NoNewPrivileges, ProtectSystem=strict, MemoryMax=256M, Restart=on-failure. Verify it restarts automatically when killed.
python3 -c "from flask import Flask; app=Flask(__name__); app.route('/health')(lambda: 'OK'); app.run(port=8080)"
vim /etc/systemd/system/labapp.service # write hardened unit
systemctl enable --now labapp && systemctl status labapp
kill -9 $(pgrep -f labapp) && sleep 3 && systemctl status labapp
✓ VERIFY: systemd-analyze security labapp.service shows low exposure score. Service auto-restarts after kill.
LAB 05 — NETWORKING & FIREWALL
Configure full network security between lab nodes
On lab-web: configure nftables to: allow SSH only from 192.168.100.0/24, allow port 8080 from lab-lb only, allow port 5432 to lab-db only, log and drop everything else. Verify from lab-attacker that port 8080 is not reachable.
nft flush ruleset
nft add table inet filter
nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input ip saddr 192.168.100.0/24 tcp dport 22 accept
nft add rule inet filter input ip saddr 192.168.100.10 tcp dport 8080 accept
✓ VERIFY: From lab-attacker: nmap -p 8080 192.168.100.20 shows port filtered. From lab-lb it shows open.

LAB 10 — BACKUP, RESTORE & DISASTER RECOVERY
Test your RPO/RTO — can you recover from disaster?
Simulate database corruption on lab-db. Time your full recovery: pg_dump restore to a specific point. Then practice file system backup with borg. Finally, simulate complete VM failure and rebuild from scratch using your Ansible playbook.
# Create backup BEFORE disaster pg_dump -U postgres appdb > /backups/appdb_$(date +%Y%m%d).sql borg init --encryption=none /backups/borg-repo borg create /backups/borg-repo::lab-$(date +%Y%m%d) /etc /var/www /opt
# Simulate disaster sudo -u postgres psql -c "DROP DATABASE appdb;" # database gone!
# Time your recovery (RTO measurement) time sudo -u postgres psql -c "CREATE DATABASE appdb;" time sudo -u postgres psql appdb < /backups/appdb_$(date +%Y%m%d).sql
# Verify recovery sudo -u postgres psql -d appdb -c "\dt" # tables should be back
✓ VERIFY: Record your actual RTO. Was it under 5 minutes? What would RPO be if disaster happened 1 hour after last backup?
