⚡Process Lifecycle — Birth, States & DeathPANEL 01
ℹEvery process in Linux descends from systemd (PID 1) via fork(). A process is the kernel's unit of resource ownership — it has its own PID, address space, file descriptors, and credentials. Threads share the address space but each has its own kernel task struct.
Process Birth → Execution → Termination
fork()
kernel clones parent address space (copy-on-write). Child gets new PID, inherits FDs, signal handlers, env.
→
exec()
replaces child's memory with new program binary. COW pages discarded. argc/argv/envp set up.
→
RUNNING
CFS scheduler grants CPU timeslice. Process executes instructions in user-space Ring 3.
→
WAITING
blocked on I/O, sleep(), mutex, network. Moved off run queue. Woken by IRQ or signal.
→
exit()
releases memory, closes FDs, sends SIGCHLD to parent. Entry stays as zombie until parent calls wait().
→
reaped
parent calls wait()/waitpid(). Kernel removes PCB. PID released back to pool.
All Process States (ps STAT column)
R
Running / Runnable
On CPU or in run queue waiting for CPU timeslice. R+ = foreground process group leader.
S
Interruptible Sleep
Waiting for event (I/O complete, timer, signal). Can be woken by a signal. Most daemons spend time here.
D
Uninterruptible Sleep
Cannot be killed with SIGKILL. Waiting for hardware I/O (disk, NFS). High D count = storage bottleneck or NFS hang.
Z
Zombie
Process exited but parent hasn't called wait(). Holds PID and exit status only. Many zombies = parent bug or resource leak.
T
Stopped
Paused by SIGSTOP or Ctrl+Z. Resume with SIGCONT or fg. Also set by ptrace debugger attach.
State Transition Map
NEW ──fork()──▶ R Runnable
R ──I/O wait──▶ D Uninterruptible
R ──event wait──▶ S Interruptible
S ──event/signal──▶ R
D ──I/O complete──▶ R
R ──SIGSTOP/Ctrl+Z──▶ T
T ──SIGCONT/fg──▶ R
R ──exit()──▶ Z Zombie
Z ──parent wait()──▶ GONE (reaped)
Modifier flags in ps STAT column:
s = session leader    l = multi-threaded
N = low priority (nice)   < = high priority

📡Signals — Asynchronous Process NotificationPANEL 02
How Signals Work
A signal is a software interrupt — an asynchronous notification delivered to a process. The kernel sets a pending signal bit in the process's task struct. When the process returns from kernel mode, pending signals are checked and delivered.

Each signal has a default action: terminate, core dump, stop, or ignore. Processes can handle most signals with a custom handler (sigaction) or block them temporarily — except SIGKILL (9) and SIGSTOP (19) which are always delivered.
Signal Delivery Path
1. Sender calls kill(pid, sig) or keyboard (Ctrl+C)
2. Kernel sets pending bit in target's task_struct
3. On next return to user-space: kernel checks TIF_SIGPENDING
4. If signal is blocked → stays pending. If not → check handler:
5a. Default action (SIG_DFL) → terminate/stop/ignore
5b. Custom handler → kernel sets up user-space stack frame, calls handler
5c. SIG_IGN → discard
Signal#DefaultCatchableCommon Use — Enterprise Context
SIGHUP1Term/ReloadYesReload config without restart: kill -HUP $(pidof nginx) — nginx re-reads nginx.conf, zero downtime
SIGINT2TerminateYesCtrl+C from terminal. Process can catch to do cleanup before exit.
SIGQUIT3Core dumpYesCtrl+\. Like SIGINT but produces core dump for debugging.
SIGSEGV11Core dumpYesSegmentation fault — invalid memory access. Indicates bug. Check coredump with gdb.
SIGTERM15TerminateYesGraceful shutdown. systemctl stop sends SIGTERM first, waits TimeoutStopSec, then SIGKILL.
SIGKILL9TerminateNOImmediate kill. Cannot be caught, blocked, or ignored. Last resort — may leave resources dirty.
SIGSTOP19StopNOPause process. Cannot be caught. Used by debuggers (ptrace) to pause target.
SIGCONT18ContinueYesResume stopped process. Shell sends this on fg or bg commands.
SIGUSR1/210/12TerminateYesApplication-defined. Apache: rotate logs. Many apps: trigger debug dump or stats output.
SIGCHLD17IgnoreYesChild changed state. Parent must handle to reap zombies (call wait()). Ignored by default in most shells.
SIGALRM14TerminateYesTimer expired (alarm() syscall). Used for timeouts in network code.
SIGPIPE13TerminateYesWrite to pipe/socket with no reader. Daemons SIG_IGN this to avoid crash on client disconnect.

👻Daemons — Background Service ProcessesPANEL 03
ℹA daemon is a long-running background process that provides a service. It detaches from its controlling terminal (setsid), runs as a non-root service account, closes stdin/stdout/stderr, and listens for work. All daemons on modern Linux are managed by systemd.
🌐
nginx / apache2
Web server daemon. Forks worker processes. Master manages workers via signals.
🔑
sshd
SSH daemon. Forks child per connection. Child drops to user privilege.
🗄
mysqld / postgres
Database daemon. Manages connections, transactions, WAL journal.
🐳
dockerd
Container daemon. Manages cgroups, namespaces, overlay FS per container.
⏰
crond
Cron daemon. Wakes every minute, checks crontab, forks jobs.
🌍
NetworkManager
Network config daemon. Manages interfaces, DHCP, VPN via D-Bus.
📋
auditd
Audit daemon. Receives kernel audit events, writes to /var/log/audit/.
📝
rsyslogd
Syslog daemon. Receives log messages via socket, routes to files/remote.
Daemon anatomy — how a daemon daemonizes itself

⚙systemd — Complete Service Management Deep DivePANEL 04
systemd Architecture
systemd is PID 1 — the init system, service manager, journal, socket activator, timer, and device manager in one. It starts all other processes and adopts orphaned ones.

Key design: parallel activation — services start simultaneously when their socket is ready, not sequentially. Socket activation: systemd creates the socket, passes it to the service when it starts — clients never see "connection refused".

State stored in cgroups — every service unit gets its own cgroup slice. systemd can track and kill all processes spawned by a service, including grandchildren.

.timer — scheduled execution (cron replacement)

.slice — cgroup resource hierarchy
.scope — externally created process groups (sessions)

⏰Cron & systemd Timers — Scheduled Task ManagementPANEL 05
Cron Anatomy
crond wakes every minute, reads all crontab files, and forks a shell for any matching jobs. Jobs run with the user's environment and permissions (or root for system crontabs).

Files: /etc/crontab (system, has username field), /etc/cron.d/ (package crontabs), /var/spool/cron/crontabs/ (per-user via crontab -e), /etc/cron.{hourly,daily,weekly,monthly}/ (run-parts directories).
systemd Timers (Modern cron)
Timers (.timer units) are more powerful: monotonic (relative: OnBootSec, OnUnitActiveSec) or realtime (calendar: OnCalendar=daily). Integrated with journald logging. Accurate to milliseconds. Persistent across reboots.

Each timer activates a corresponding .service unit. Check with systemctl list-timers.

📊cgroups & Resource Limits — CPU, Memory, I/O ControlPANEL 06
Control Groups (cgroups v2)
cgroups are a kernel mechanism to group processes and enforce resource limits. Every systemd service gets its own cgroup. Resource controllers: cpu (quota/shares), memory (max/high), io (bandwidth), pids (process count).

Hierarchy: slices → services → scopes. system.slice holds all system services. user.slice holds user sessions. Each slice limits its children collectively.
ulimit — Per-Process Limits
ulimit sets limits for the current shell and children. Soft limit: current limit (user can lower). Hard limit: ceiling (only root can raise).

Critical limits: nofile (open FDs — too low = EMFILE errors), nproc (process count — too low = fork bomb protection), core (core dump size), stack (stack size).

Scenario A — CPU Runaway at 3AM
Alert: Server load average 28 on 4-core system. SSH barely works.

1. uptime → load: 28.4, 19.2, 11.3 (growing)
2. ps aux --sort=-%cpu | head -5 → PID 8841 python3 at 780% CPU
3. cat /proc/8841/cmdline → crypto miner (malware!)
4. kill -9 8841 → immediate relief
5. last + ausearch → trace how it got there
6. find / -newer /etc/passwd -type f 2>/dev/null → find dropped files
Root cause: Compromised web app ran RCE payload. Hardened cgroups + CPUQuota would have limited blast radius.
Scenario B — Service Crash Loop
Alert: myapp.service failed 3 times in 60s — systemd gave up.

1. systemctl status myapp → failed, exit-code=1
2. journalctl -u myapp -n 50 → "Cannot connect to database"
3. systemctl status postgresql → OOM-killed by kernel
4. dmesg | grep -i "killed process" → postgres OOM
5. free -h → only 120MB RAM free
6. ps aux --sort=-%mem | head -5 → java heap leak
Fix: Add MemoryMax to java service. Set StartLimitBurst=5 and alert on StartLimitHit.
Scenario C — Fork Bomb Attack
Attack: :(){ :|:& };: — bash fork bomb from compromised user

Effect: PID table exhausted → no new processes possible → effectively DoS

Prevention:
/etc/security/limits.conf:
* hard nproc 200

systemd protection:
TasksMax=200 in user slice or session scope

Detection: watch -n1 'ps aux | wc -l' — rapid process count growth
Scenario D — Zombie Accumulation
Symptom: 2000+ zombie processes. PID table at 80% capacity.

1. ps aux | grep Z | wc -l → 2147 zombies
2. ps -eo pid,ppid,stat | awk '$3~/Z/{print $2}' | sort -u → all zombies have PPID 4201
3. ps -p 4201 -o comm → "workerd" (custom process pool)
4. Bug: worker pool not calling waitpid() after child exit
Fix: Signal parent: kill -SIGCHLD 4201 — triggers wait() if handled. Else restart the pool with a patched binary.

🔒Security Perspective — Process & Service Attack VectorsPANEL 10
Red Team — Process Attacks
  • ›
    Cron backdoor: plant * * * * * /tmp/.hidden/shell.sh in any writable crontab — executes every minute. Hard to detect without comprehensive cron audit.
  • ›
    Process masquerading: rename malware to sshd or [kworker/0:0] (kernel thread notation) to hide in ps output. Check /proc/PID/exe for true binary path.
  • ›
    Malicious systemd unit: drop /etc/systemd/system/evil.service + enable → persistent across reboots, starts before most defenses.
  • ›
    LD_PRELOAD hijack: set in /etc/environment or per-user .bashrc → custom shared library loaded into every process — intercept system calls.
  • ›
    Fork bomb DoS: exhaust PID table → system unresponsive. Requires no privileges beyond shell access.
Blue Team — Process Hardening
  • ›
    Audit ALL cron sources weekly: /etc/crontab, /etc/cron.d/, all user crontabs, at jobs, systemd timers
  • ›
    Check /proc/PID/exe for deleted or replaced binaries: ls -la /proc/*/exe 2>/dev/null | grep deleted
  • ›
    Enforce TasksMax per user slice: UserTasksMax=200 in /etc/systemd/logind.conf
  • ›
    Audit systemd units: systemctl list-units --type=service --all → look for unknown units
  • ›

◉Summary — Step 5 CompletePANEL 13
Process Lifecycle & Signals
Every process: fork() → exec() → run → exit() → reaped by parent. Five states: R/S/D/Z/T. SIGKILL and SIGSTOP are uncatchable. SIGHUP reloads config. Signals are the primary IPC between admin and daemon.
systemd & Service Security
systemd is PID 1, service manager, journal, timer, and cgroup controller. Hardened unit files: NoNewPrivileges, PrivateTmp, ProtectSystem=strict, CapabilityBoundingSet, SystemCallFilter, IPAddressDeny. MemoryMax prevents OOM cascade.
Cron, cgroups & Threat Hunting
Cron is a top persistence mechanism — audit ALL sources. cgroups v2 enforces CPU/memory/pid limits per service. Detect threats: /proc/PID/exe deleted, LD_PRELOAD in environ, unknown systemd units, external C2 connections via ss.
